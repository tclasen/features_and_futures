# Workboard

Requires Node.js 22.22.1. No external dependencies or installation step.

## Run

```sh
PORT=8080 DB_PATH=./data/workboard.sqlite npm start
```

Open `http://localhost:8080`. The server binds to `0.0.0.0`; `PORT` defaults to 8080 and `DB_PATH` defaults to `./data/workboard.sqlite`. Keep the configured SQLite file to preserve projects, archive state, tasks, and completion state across restarts. Existing databases are automatically upgraded with active projects, Normal task priorities, and Normal project defaults, empty task due dates and notes, and live task deletion state without changing existing task data. Its parent directory is created automatically.

`GET /health` returns HTTP 200 with `{"status":"ok"}`.

The application uses server-rendered HTML and native forms. SQLite assigns an internal sequence for stable project ordering and remembers each task's position separately in every project it has belonged to. Existing task order is migrated without changes. First-time arrivals and newly created tasks append after all established positions, including positions of tasks currently elsewhere; returning tasks reuse their remembered positions. Task creation and movement save ownership and ordering atomically. Public IDs are UUIDs and never change on a move. Project names and task titles are trimmed before saving and escaped when rendered. Active project pages provide a New project name field and Rename project button. Renaming preserves the URL, creation order, tasks, completion state, and summaries; blank names are rejected. Each project page supports task creation, saved completion checkboxes, and All, Open, Completed, and Deleted filters. Each task row provides a New task title field and Rename task button. Task renaming trims and validates the title, updates the completion label, and preserves ownership, order, completion, and summaries. Each task provides a Task due date textbox and Save due date button. Empty or whitespace-only values clear the date; other values are trimmed and must be real Gregorian days in YYYY-MM-DD format with years 0001–9999. Dates are saved as calendar-day strings without timezone conversion; invalid values leave the saved date unchanged. Date edits preserve all other task data and both filters. Each task also has an independently saved Task priority selector with Low, Normal, and High options. Each project has a saved Default task priority selector with the same options, initially Normal. New tasks inherit their project's current default; changing a default never changes existing tasks. Defaults remain independent between projects and survive renaming, archival, restoration, and restarts without resetting either task filter. Each project page also provides a Priority filter with All, Low, Normal, and High options. Completion and priority filters combine, retaining creation order and both selections during task edits. Opening a project starts with both filters set to All. Priority and completion edits immediately re-evaluate matching rows; summaries always count all live tasks. Each project page also provides Due from and Due through textboxes and an Apply due range button. Applied boundaries are inclusive and intersect the completion and priority filters. A blank boundary is unbounded; undated tasks match only when both boundaries are blank. Boundaries use the same Gregorian validation as task dates; invalid or reversed ranges show an alert and preserve the previous applied range and membership. All edits retain the applied range, and date, priority, or completion edits immediately re-evaluate matching rows. Opening a project from the list resets the range to empty. Range controls remain usable when archived. Filter selections and the applied range are carried in the page URL and forms, not saved as task data. The project list defaults to Active, with an Archived filter and archive/restore controls. Project summaries count completed and total live tasks, regardless of filters. Archived project pages retain task filtering but disable project and task renaming, task creation, completion changes, priority edits, due-date edits, and default-priority changes, including direct POST requests. Restoring a project preserves its tasks. Each task row provides a Destination project selector listing only other active projects in project creation order, using their current names, and a Move task button. Moving to a new project appends the task; returning to a previous project restores its relative ordering position, even when multiple tasks return in a different order. Moves preserve the current ID, title, completion, priority and due date, and update both summaries. Remembered positions survive project renaming, archival, restoration, and server restarts; returning never restores older task field values. The source page stays open with its filters and applied range retained. Move controls are disabled for archived sources or when no eligible destination exists; direct requests also reject archived, missing, or same-project destinations and tasks not owned by the source. Small browser event handlers submit completion, priority, and filter changes automatically. Completion changes save immediately in a serialized request queue with keepalive enabled. Filtered rows refresh in place after a brief 150 ms interaction delay; checkbox saves never schedule navigation that could abort an explicit reload. Other fields and unsaved inputs remain untouched. Subsequent form actions (including deletion and export) wait for pending completion saves, preventing a quick action from discarding or overtaking the checkbox change. Failed saves show an alert and block dependent actions rather than silently losing completion state.

## Task deletion

Live task rows provide `Delete task`. Deletion keeps all saved fields, ownership, and remembered positions but removes the task from All/Open/Completed and completion summaries. `Deleted` shows only deleted tasks, intersecting priority, due-range, and title search filters. Deleted rows show saved fields with all editing and movement controls disabled; direct requests also reject edits and moves. `Restore task` makes the task live at its reserved position, without changing fields or resetting filters. Tasks created while it was deleted follow its reserved position. Archived projects permit reading and filtering but disable deletion and restoration. Archive/restore never changes task deletion state. Upgrades initialize existing tasks as live, and deletion state survives reloads and restarts.

## Task notes

Each task row provides a `Task notes` textarea and `Save notes` button. Notes are optional plain text, saved without trimming, escaped for display, and preserved through edits, moves, return ordering, reloads, and restarts. Saving retains all applied filters and search; notes are not searched. Archived projects disable notes editing and reject direct notes updates. Database upgrades add empty notes without changing existing data.

## Search

The project list provides `Project search` and `Search projects`; each project page provides `Task search` and `Search tasks`. Applied queries match substrings, trimming surrounding query whitespace and ignoring ASCII letter case. For matching only, runs of ASCII spaces and horizontal tabs in both queries and saved names/titles become one space. Other internal whitespace and non-ASCII characters remain significant. Saved names/titles and their display are never rewritten by search. Blank queries match everything. Project search intersects Active/Archived; task search intersects completion, priority, and the applied due range. Searches preserve ordering and never affect saved data or all-live-task summaries. Queries are carried in URLs and forms through filter changes, edits, and validation failures. Archived projects still allow searching. Opening a project from the list or returning with `Projects` resets the corresponding query to empty.

## Project export

Every project page provides `Download project`, including archived projects. `GET /projects/<id>/export` downloads UTF-8 `workboard-project.json` with format `workboard-project`, version `1`, and the current project name, archive flag, default priority, and all live/deleted tasks in their stored project order. Each task includes title, completion, explicit priority, due date, notes, and deletion state. Export ignores view filters and searches, omits identities and remembered positions, and changes no stored data. Notes line endings are normalized to LF only in the exported representation; other characters remain exact. Empty projects have an empty tasks array.

## Project import

The home page provides `Project JSON`, `Imported project name`, and `Import project`. Paste a version-1 portable export and supply a nonblank name override. `POST /imports/projects` validates every required field and every task before writing, then creates a new independent project with fresh identities in one SQLite transaction and opens it. The override is trimmed; imported nonblank titles are preserved exactly, and notes line endings become LF. Archive state, default priority, live/deleted task order and all task fields are retained. Additional properties cannot set internal identities or positions. Malformed documents display `Invalid project JSON`; blank overrides display `Project name is required`. Both failures preserve submitted fields and leave all data unchanged. Imported copies use the same archive restrictions, task restoration, movement and remembered-order rules as ordinary projects.

## Task directory

`Task directory` on the home page opens `/directory`, a cross-project view with read-only rows and bulk completion, deletion, restoration and priority actions. Each opening starts with Active project scope, All task and priority filters, Original directory order, and empty due range and title search. Scope, live/deleted completion, priority, inclusive due range, and normalized title-only search intersect without modifying data. Invalid ranges preserve the applied range and results. Rows show the original owner, title, completion, priority, due date, and literal multiline notes, in project creation order and remembered task order. `Open project` opens the owner with default project filters; `Projects` returns to the home page. Archived and deleted tasks remain readable without editable row controls.

`Complete visible tasks` and `Reopen visible tasks` update only the completion of matching live tasks in active projects. Both actions resolve the current intersection of filters, search and applied range on the server and save changes atomically, retaining the view state. Controls are disabled for Archived scope, Deleted filter, or when no matching task needs that action; direct requests cannot bypass archive/deletion restrictions. Result membership and project summaries reflect the saved state. Empty resolved results announce `No matching tasks`. Native form navigation hides the old empty announcement while the next response is loading; each server-rendered response contains only resolved results.

`Delete visible tasks` soft-deletes matching live tasks in Active scope under All, Open or Completed. `Restore visible tasks` restores matching deleted tasks only under Active scope and Deleted. Both resolve all current filters/search/range on the server and update flags atomically across original owners. Controls are disabled outside their eligible scope/filter or for empty results, and direct requests enforce the same scope/filter restrictions. Actions retain directory ordering and all controls, refresh task and owner rows, totals and eligibility, and preserve every other field, original identity and reserved position. Project summaries exclude deleted tasks; restored tasks regain their reserved order even after later creation or moves. Duplicate owner names remain independent. Integration tests cover all live filters, exact field preservation, nonmatching and archived protection, empty results, independent same-name owners, exports, moves/returns and real process restarts.

`Visible tasks priority` offers Low, Normal and High, initially Normal on every fresh visit. `Set visible priority` atomically updates only matching live tasks in Active scope, using all current completion, priority, due-range and title-search controls. Archived, Deleted and empty live results disable the action; direct requests reject protected scopes and missing or invalid priorities. The matching set is resolved before edits, so changed rows may leave the priority-filtered result. All filters, ordering and the selected bulk priority are retained; rows, owner/global totals, empty state and action eligibility refresh from saved data. Only task priority changes, leaving defaults, other fields, identities and remembered positions intact. Integration tests verify independent same-name owners, field preservation, invalid input, protected/nonmatching records, empty results, moves/returns and real server restarts.

`Directory order` offers Original, Priority (High, Normal, Low), Due date (ascending, undated last), and Title (ASCII-case-folded literal Unicode code point order). Ties retain Original order across the entire result. Ordering survives filter, search, range and bulk-action changes, including validation errors, but never changes stored task order, exports or remembered return positions. A new directory opening resets to Original.

The read-only `directory-summary` displays `{completed}/{total} completed` for exactly the resolved matching rows, including retained completion flags in Deleted views. It updates with filters, search, range and bulk actions; ordering does not affect counts. Empty results show `0/0 completed` alongside `No matching tasks`. Project summaries still count only their own live tasks.

The separate matching-project list provides one `directory-owner-row` per represented project, with its literal name, matching-task completion summary, and `Open project` navigation. Owners remain in project creation order regardless of directory task ordering. Counts use only the current resolved intersection, including Deleted and Archived results; empty results have no owner rows. Grouping uses project IDs, so duplicate names remain independent. Project creation and renaming allow duplicate names without changing identities or order.
