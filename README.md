# Workboard

A dependency-free project board using Node.js 22.22.1, built-in HTTP, and SQLite.

## Run

```sh
npm start
```

The server binds to `0.0.0.0`, with `PORT` defaulting to `8080` and `DB_PATH` defaulting to `data/workboard.sqlite`. Parent database directories are created automatically. Set `DB_PATH` to a persistent, writable file location to retain projects, tasks, and completion state across restarts.

```sh
PORT=8080 DB_PATH=./data/workboard.sqlite npm start
```

Open `/` to create and open projects. `GET /health` returns `{"status":"ok"}`. Project pages support task creation, completion checkboxes, and an All/Open/Completed/Deleted filter. A separate All/Low/Normal/High priority filter combines with the completion filter; both selections survive edits, and matching tasks retain creation order. Filters remain usable when archived and never affect saved data or completion summaries. Opening a project from the list starts both filters at All. Tasks belong to their project and display in established project order: first arrivals append, while returning tasks recover their previous positions. The project list filters Active/Archived projects and shows completion totals for all live tasks. Archive/restore preserves tasks; archived pages allow viewing and filtering but disable task creation and completion changes. Active project pages also support renaming with trimmed, nonblank names; renaming preserves the URL, creation order, tasks, and summary. Each task row also supports renaming with a trimmed, nonblank title, preserving its ownership, order, completion state, and filter membership. Each task also has a Low/Normal/High priority selector. Each project has a saved Default task priority selector, initially Normal, which applies only to subsequently created tasks. Changing a default preserves existing tasks and both filter selections; defaults are independent per project and persist through renaming, archival, restoration, and restarts. Priority changes persist independently without affecting completion, order, ownership, or summaries; renaming preserves priority. Archived pages disable project and task renaming, task priority changes, and the project default priority selector until restoration. These restrictions are also enforced by the server. Existing databases are upgraded automatically while preserving IDs. Pages use native HTML forms; a small browser script submits completion, priority, and filter changes automatically. SQLite assigns permanent IDs. Names and titles are trimmed on the server and escaped when rendered.

Each task row includes an optional Task due date textbox and Save due date button. Dates are trimmed and validated as real Gregorian `YYYY-MM-DD` days (years `0001`–`9999`), without timezone conversion. Blank input clears the saved date; invalid input shows an alert and preserves it. Dates persist independently through other edits and restarts, without affecting completion or priority filters or summaries. Archived projects disable due-date edits in both the UI and server.

Project pages also provide Due from and Due through textboxes and Apply due range. Applied boundaries are inclusive and combine with completion and priority filters. Blank boundaries are unbounded; undated tasks match only when both boundaries are blank. Invalid dates or a reversed range show an alert and leave the previously applied range unchanged. The applied range is carried in navigation URLs and hidden form fields, not saved task data. Edits retain all filters and immediately re-evaluate membership. Archived projects permit range filtering, and opening a project from the list starts with empty boundaries.

Each task row provides Destination project and Move task controls. Destinations list only other active projects, in project creation order using their current names. Moving to a new project appends the task; returning to a previous project restores its remembered position without changing its current identity, title, completion, priority, or due date. The source stays open with all filters retained, and both summaries reflect current ownership. Archived projects cannot send or receive tasks; move controls are disabled when archived or when no eligible destinations exist. The server also validates source ownership and active destinations. The SQLite task_positions table remembers each task's position separately for every project it has belonged to, including while it is away. New tasks and first arrivals append after all established positions, not just currently resident tasks. Ownership and position changes are transactional. Migration seeds remembered positions from the existing task order; the legacy tasks.position column is retained but no longer used for ordering.

Project search and Search projects filter project names alongside the Active/Archived filter. Task search and Search tasks filter titles alongside completion, priority, and the applied due range. Both use substring matching that ignores ASCII letter case and trims surrounding query whitespace. Runs of ASCII spaces and horizontal tabs in queries and saved names/titles match as one space; other internal whitespace and non-ASCII case remain significant. This matching normalization never rewrites saved names/titles or their display. Blank queries match everything allowed by the other filters. Applied queries travel in URLs and hidden form fields, never in stored task data. Task edits and moves retain the query and re-evaluate membership without changing summary counts. Search stays usable in archived projects. Opening the list through Projects or opening a project from the list starts with an empty query.

Each task has a multiline Task notes textarea and Save notes button. Notes are saved as plain text without trimming, including whitespace, Unicode and literal markup; empty text clears them. Notes persist through edits, movement, remembered returns and restarts, and do not participate in search. Saving retains every applied filter. Archived projects display notes with editing disabled, enforced by both UI and server. Database upgrades initialize only the new notes field to empty without changing existing task data.

Live task rows provide Delete task; deleted rows provide Restore task. All, Open and Completed show only live tasks, while Deleted intersects the same priority, date range and title search filters. Deletion retains all saved fields and remembered positions but removes the task from completion summaries. Restoration recovers its reserved order, even before later-created tasks, without applying a changed project default. Deleted task editing and moving are disabled and rejected by the server. Archived projects permit reading deleted tasks but cannot delete or restore them. Deletion state persists independently of project archival; upgrades initialize earlier tasks as live.

Every project page offers Download project, including archived and empty projects. It downloads UTF-8 `workboard-project.json` with `format: "workboard-project"`, `version: 1`, and the project's name, archive state, default priority and all currently owned live/deleted tasks in remembered order. Tasks contain title, completion, priority, due date, notes and deletion state; internal IDs and remembered positions are not included. Notes line endings become LF only in the export. Downloads ignore all page filters and searches and never change stored data or the current page. `GET /projects/<id>/download` returns the JSON attachment, or 404 for an unknown project.

The home page provides Project JSON, Imported project name and Import project controls. Imports require a trimmed nonblank override name and a complete version-1 portable document with correctly typed required fields and valid calendar dates. Validation finishes before any writes; project creation, task creation and reserved ordering positions are committed together. Invalid submissions show an alert and retain both entered fields without changing data. Successful imports open a new independent project, preserving archive state, defaults, exact titles, all task fields and supplied order. Notes use LF line endings. Extra properties cannot set internal IDs or positions. Empty task arrays are accepted; imported deleted and archived tasks retain the usual read-only restrictions.

The home page's Task directory opens `/directory`, a cross-project view with read-only task rows. Each opening starts at Active project scope, All task and priority filters, empty due boundaries and an empty Directory search. Scope, live/deleted completion state, priority, inclusive due range and title-only search intersect using the same rules as project pages; each control preserves the other applied filters. Invalid ranges retain previous membership and display the existing validation alerts. Results follow project creation order and each owner's remembered task order, and show the original title, owner, completion, priority, date and literal multiline notes. Open project navigates to the owner with default project filters. Directory viewing and filtering never write application data, and archived/deleted tasks are readable without editing controls.

Complete visible tasks and Reopen visible tasks atomically update completion for the matching live tasks in Active scope, retaining every applied directory filter. Each button is disabled when no visible task needs that action; both are disabled for Archived scope and Deleted filtering. The server independently enforces those restrictions and resolves matches using the same rules as the displayed results. Other fields and remembered positions remain unchanged. Empty resolved results announce No matching tasks; pending result updates hide that announcement and temporarily disable bulk controls to avoid acting on stale rows.

Directory order offers Original, Priority, Due date and Title, defaulting to Original on each opening. Priority sorts High/Normal/Low; dates sort ascending with undated tasks last; titles sort by literal ASCII-folded Unicode code points without whitespace normalization. Ties retain Original order across owners. Ordering remains selected through filtering, search, range validation and bulk completion, and never changes stored task positions, project views or exports.

The directory displays one read-only completion summary for its resolved results: completed matching tasks divided by all matching tasks. It includes retained completion flags in Deleted views and works identically in Archived scope. Filters, search, ranges and bulk actions refresh the counts with the rows; ordering does not change them. Empty resolved results show `0/0 completed` alongside No matching tasks.

## Verify

```sh
npm test
node --check server.js
```

Automatic GET filter changes update only the results and their bulk action controls, keeping search and due-range drafts in place. Applied selections are propagated to action forms immediately; newer selections cancel stale result requests. Ordinary form submissions still use server navigation, and automatic filtering falls back to navigation if fetching fails. `test/browser.test.js` exercises concurrent changes and submission cancellation with built-in Node tools (not a full browser acceptance run).

Tests launch the real server against a temporary database and cover health, required-name validation, trimming, creation order, HTML escaping, project navigation, task validation, completion, filtering, project isolation, archive/restore, archived mutation protection, completion summaries, project and task renaming, identity and ownership preservation, task priorities and project defaults, independent updates, inheritance only by subsequent tasks, invalid-priority rejection, all combined-filter pairs and selection retention through mutations, legacy database migration, due-date validation (including leap years and year boundaries), clearing and archived date protection, inclusive and one-sided due ranges, invalid range preservation, range intersection and retention through edits, task moves, first-arrival append ordering, reverse-order returns, independent remembered positions, new tasks created while previous tasks are away, destination eligibility and ownership validation, filter retention and summary updates after moves, project/task search matching and escaping, search intersection with archive/completion/priority/date filters, query retention through mutations and validation errors, empty-query navigation, archived search availability, and persistence across server restarts. Notes tests also cover migration, exact text preservation, safe HTML rendering, filter retention, search exclusion, ownership protection, moves and remembered returns, archival, clearing, and restart persistence. Deletion tests cover live-state migration, retained fields and filters, deleted-filter intersections, summary exclusion, disabled controls and server mutation protection, archived restrictions, reverse-order restoration into reserved positions, movement after restoration, and restart persistence. Export tests cover legacy defaults, exact names/titles and Unicode notes, portable LF conversion without stored changes, inclusion of deleted tasks independent of filters, remembered order after moves, project isolation, empty and archived exports, download headers, unchanged page state and database contents, missing projects and restart persistence. Import tests cover atomic rejection of malformed documents, missing fields, incorrect types, invalid dates and later invalid tasks; blank override names; independent IDs and state, exact fields and LF notes, summaries, restoration and remembered returns, archived and empty imports, and restart persistence. Directory tests cover default filters, intersecting scope/completion/priority/date/title searches, search exclusion of owner names and notes, inclusive and one-sided date boundaries, invalid-range membership preservation, safe literal notes, read-only row controls, imported tasks, archive/deletion visibility, remembered return order, unchanged database contents and restart persistence. Bulk directory tests cover intersected cross-project actions, button eligibility, empty results, filter retention, archive/deletion exclusions, unchanged fields and ordering, idempotence, movement after updates and real server-restart persistence. Browser-script tests verify loading hides empty announcements and disables stale bulk actions. Temporary files are removed after the test.
