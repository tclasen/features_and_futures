# Questions and evidence decisions

The engineering pilot verifies that the PM can measure complete delivery trajectories. Its three tasks and one trajectory per configuration do not estimate a maintainability effect.

The primary questions are whether stronger instructions change later builder execution time, total native-token uncached reference cost and first-submission rejection frequency within each fixed model/harness pair. Analyze maximum versus none, minimal versus none and maximum versus minimal in each of the four hosted model/harness pairs: 12 instruction contrasts and three primary outcomes. Keep all model/harness configurations in the results. Additional model/harness comparisons and sandbox DORA metrics are secondary.

For a main experiment, use the same frozen task packets for independent repeated runs, with fresh starter repositories and contexts. Exact repeats retain harness/image/stack/model mappings and reference prices. Record schedule seeds, calendar/provider changes and resource contention. Native service aliases do not prove immutable hosted model weights; causal conclusions remain conditional on recorded provider provenance.

Begin candidate inspection after 20 shared tasks, then every ten tasks. Generate each next feature before inspecting comparative outcomes. A candidate uses the last ten shared tasks and must recur in two adjacent windows. Candidate inspection is descriptive and cannot establish a stopping claim.

Confirm a candidate by replaying the frozen prefix in independent fresh runs. For each run and instruction contrast, sum all execution nanoseconds and uncached reference costs over the same ten-task late window, including retries and rejected work. Form time and cost ratios (stronger/weaker instructions), and the difference in first-submission rejection proportions. Use medians of these paired run contrasts to describe a typical trajectory. Report raw cumulative results and early investment alongside the late-window results. Keep cache-aware reference cost as a secondary outcome; native caching may depend on schedule and provider state. This estimand is not the population mean or a claim that all codebases improve.

The practical bands are 0.8 through 1.2 for time/cost ratios, and -0.10 through +0.10 for rejection-proportion differences. Use exact order-statistic median confidence intervals with two-sided binomial tails. These intervals require independent, identically distributed run contrasts; tasks within a run are dependent and are never counted as replicates. Stratify or restart confirmation when protocol/provider/environment changes invalidate those assumptions. Preserve every attempted analysis and its raw input hashes.

At confirmation look j, allocate alpha = 0.05 / (36 * j * (j + 1)) to each primary interval. The sum over all 36 contrasts and all looks is at most 0.05, so the family and repeated-look error allocation is explicit. Increment j for every confirmation analysis, including inconclusive results and added repetitions. Small samples yield unbounded intervals and no decision; do not replace these with unjustified narrow estimates. The exact interval and classification functions are in orchestrator/analysis.py, with independent mathematical checks.

A primary contrast is an improvement or regression only when the entire interval lies beyond its practical band. Practical equivalence requires the entire interval inside the band. Otherwise it remains unresolved. Continue tasks or repetitions while any of the 36 primary decisions remains unresolved. Stopping requires all primary contrasts classified and the candidate reproduced in an independent confirmation batch. There is no line-count or guaranteed-duration stopping rule. Save a versioned main manifest that references these rules before main dispatch; pilot authorization does not itself launch that main run.

Report all five sandbox DORA adaptations with actual event counts and common windows. Nominal deployment frequency is constrained by the synchronized round barrier. Pre-acceptance failures are not deployment incidents. A zero observed incident rate is supported only by a nonempty promotion denominator; recovery time remains unavailable without incidents. Broader equal post-deployment checks and an observation window must be frozen for the main run. The pilot's five-second health check gives narrow stability evidence and cannot answer every reliability question.

Infrastructure failures and provider outages are distinct from builder rejection outcomes. Their consumed time and usage remain in raw evidence and exposure totals, with replacement attempts linked. Superseding corrections change attribution, never erase costs or original observations. Missing usage, incomplete trajectories or missing deployment evidence cannot establish equivalence.

Pilot readiness requires all 12 hosted configurations to accept all three tasks; complete request-native counts; reproducible decimal pricing; verified common packet/profile delivery; successful cumulative, upgrade and restart phases; original source/history restoration; and honest unavailable DORA values. PM conversation usage is unavailable and excluded from builder cost. The current attempt wall-time boundary is PM invocation through harness/observer closure; small observer-drain overhead is included and should be separated through a process-exit event in the next execution revision.

The hosted-only family size was selected on 2026-10-09. Earlier full-matrix pilot definitions retain six model/harness pairs and 54 primary decisions. `look_alpha(j, contrasts=36)` applies the hosted family explicitly; the legacy default remains 54 for historical full-matrix checks. The main manifest must freeze the selected family size before dispatch.
